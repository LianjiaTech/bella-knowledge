## 目标

在 console 文件列表的文件节点操作菜单中提供“解析进度”，让用户能够查看该文件当前已记录的全部后处理进度，并在任务仍未结束时看到最新状态、百分比和后端消息。方案不改变后处理任务、进度写入或上传时的 `post_processors` 配置，同时保持文档解析页面现有的单项进度查询和轮询行为兼容。

## 方案

### 1. 以服务端返回的全部进度为事实来源

选择后端按文件查询全部进度，而不是在 console 固定维护进度名称列表。`file_progress` 已按 `(file_id, name)` 存储多种后处理记录，固定名称列表会漏掉新增后处理类型，也会把“没有记录”和“任务失败”混为一谈。

- 在 `FileRepo` 增加按 `file_id` 查询全部 `file_progress` 的方法，按数据库记录的更新时间及名称提供稳定排序；转换为现有 `Progress` DTO，字段保留 `fileId`、`name`、`status`、`message`、`percent` 等后端字段。
- 在 `FileService` 增加批量进度查询入口，继续复用 `requireContentFile`，避免绕过既有文件存在性、归属和内容节点校验。
- 在 `FileController` 新增不带 `progress_name` 的按文件查询接口，建议路径为 `GET /v1/files/{file_id}/progresses`，响应体为 `Progress[]`；空记录返回 `200` 和空数组，不把“尚未产生进度”当成异常。
- 保留现有 `GET /v1/files/{file_id}/progress?progress_name=...` 及其单项 `Progress` 响应、找不到进度时的错误语义。文档解析页面继续通过现有 Next.js 代理请求 `document_parser`，不改其返回契约；新增接口和旧接口都复用相同的可追踪 purpose 校验及文件鉴权上下文。
- 为 console 增加独立的 `/api/files/{fileId}/progresses` 代理，仅转发当前工作区、Cookie、console 标识和后端错误，不在代理层硬编码进度名称。请求失败应保留后端错误消息，供模态框展示“查询失败”及诊断信息。

### 2. 明确可追踪节点范围和菜单边界

“解析进度”只对 `node_type === "file"` 展示。当前 `FilenameCell` 已将目录、文件、资源引用区分为 `directory`、`file`、`resource`；后端进度接口要求 `requireContentFile`，目录没有文件内容，资源引用也不是可直接查询进度的内容节点，因此不能把资源引用的展示名称或引用标识当作进度查询 ID。

- 文件节点显示入口；目录和资源引用隐藏入口，而不是让用户点击后才看到后端异常。
- 菜单项、触发按钮及其回调均调用 `stopPropagation`，并使用独立的受控模态框状态；选择菜单项只关闭下拉菜单并打开进度模态框，不触发行选中、文件预览或目录进入。
- 进度模态框标题显示文件名；关闭时清除当前文件、请求错误和进度列表，避免重新打开时短暂展示上一个文件的数据。
- 该边界与 console 当前 `/api/files` 固定查询 `purpose=assistants` 的文件列表一致；本次不扩大后端 `allowedProgressTrackablePurposes()` 范围。若未来列表允许展示其他 purpose，由后端 purpose 校验和新的产品需求决定是否开放，而不是由前端猜测。

### 3. 统一进度数据转换和显示规则

在 `web/src/request/files.ts` 外提取一个小型进度领域类型/转换模块，API 类型与渲染模型分离。API 模型允许后端字段为空或出现未知值；渲染模型负责稳定文案和安全边界。

- 名称映射集中维护已知文案，例如 `document_parser` 显示“文档解析”，`file_indexing` 显示“文件索引”；未知名称显示原始名称并标注“未知后处理”，不得因为新增名称而不渲染或请求失败。
- 状态保留原始值，并将已知状态归一为“尚未开始”“处理中”“已完成”“失败”。兼容当前已确认的 `document_parse_finish`、`document_parse_failed`，并为常见的 pending/processing/running 及 finish/failed 后缀提供映射；未识别状态显示原始状态值和“未知状态”，不擅自判定为成功。
- 百分比仅接受有限数值；`null`、非数字和无法解析的值显示“—”，小于 0 按 0、大于 100 按 100，防止进度条越界。消息为空时不渲染空占位；有消息时完整展示，尤其保留失败原因。
- 每一项至少展示名称、百分比、状态和 message；列表为空时展示“暂无进度数据”，而不是把空数组当作查询失败。
- 未完成判断以归一后的终态为准。未知状态或缺少状态的项目默认视为未完成，避免过早停止刷新；所有项目均为已完成或失败时停止刷新。

### 4. 打开即查、未完成时轮询并严格清理

进度模态框采用“打开立即查询 + 未完成自动轮询”的交互，既满足打开时读取最新值，也能覆盖文件上传后异步解析/索引的过程。

- 首次打开进入 loading，调用一次全部进度接口；响应成功后按转换规则渲染多条记录、空数据或已完成结果。
- 空数组分为“等待首条记录”和“确实无进度”两个阶段：打开后若返回空数组，先显示“等待后处理开始”，按 1 秒间隔继续查询，最多等待 30 秒（30 次请求）；期间一旦返回记录，立即切换为正常进度展示并按记录状态决定后续轮询，超时后停止请求并显示“暂无进度数据”，同时提示可重新打开查看。这样覆盖上传完成但 `updateProgress` 尚未首次写入的竞态，不会把短暂空结果误判为终态。
- 只要至少一项不是已完成/失败，就以 1 秒间隔再次查询；单次请求完成后再安排下一次，不使用可重入的并发 `setInterval`，确保不会出现重复请求。
- 网络或后端错误展示查询失败和错误消息；错误不清空最后一次成功数据，并按 1 秒、2 秒、4 秒递增退避，最大 8 秒，连续失败后仍保持模态框可关闭。成功响应恢复 1 秒间隔。
- 关闭模态框、切换到其他文件、组件卸载、请求被替换，以及所有项目进入成功/失败终态时，均清除 timeout、取消/忽略未完成请求并阻止旧响应写入新状态。
- 轮询只负责读取，不提供取消、重试或手工触发后处理；模态框中的“关闭”是唯一操作。

### 5. 前后端拆分和验证范围

实现按职责拆分，避免把接口、状态转换和文件列表交互继续堆在 `columns.tsx`：

- 后端：`FileRepo` 查询全部记录，`FileService` 负责文件校验与 DTO 转换，`FileController` 暴露新接口；旧单项接口不改。
- Web 请求层：`web/src/request/files.ts` 增加全部进度的类型化请求；新增 Next.js route 代理；保留并复用现有 `getFileProgress`。
- Web 领域/UI：新增进度类型转换和状态文案模块；新增进度模态框组件；`FilenameCell` 只负责文件节点菜单入口和打开回调；`page.tsx` 或邻近容器负责受控模态框生命周期，避免表格行重渲染导致轮询重复启动。
- API 测试：沿用 `api/src/test/java/com/ke/bella/files/api` 的 MockMvc/Mockito 风格，覆盖全部进度返回多项记录、空数组、不可追踪 purpose/鉴权失败、单项接口仍按原参数返回及单项不存在的原错误语义；必要时补充 `FileRepo` 查询排序测试。
- Web 转换测试：为纯转换函数建立可执行的最小前端测试入口（优先沿用仓库现有测试基础设施；当前 `web/package.json` 未配置测试 runner，若无可复用 runner，则引入轻量 runner 和 `test` 脚本，不把测试逻辑放进组件）。至少覆盖多种名称/状态、未知名称、空值和非法百分比、失败 message。
- Web 交互校验：为模态框请求状态和轮询生命周期补充组件测试；至少验证 loading、空数据后出现活动记录、空数据等待超时、查询失败、单项失败、终态停止、关闭清理、切换文件不串数据，以及菜单点击不触发行选中。没有组件测试环境时，使用现有 lint/type-check 加可测试的请求/转换边界，并在 PR 中明确覆盖范围。
- CI/本地校验：运行后端相关测试、`web` 的 `npm run type-check`、`npm run lint:check` 和新增的前端测试命令；不修改上传、重传、重命名、移动、删除和目录浏览逻辑，仅通过回归验证确认这些入口未受影响。

## 验证

验收以以下场景为准：

1. 文件节点的 `...` 菜单可见“解析进度”；目录和资源引用不可见；点击后下拉菜单正常关闭、文件行不被选中、文件名不触发预览/进入目录。
2. 后端为同一文件返回 `document_parser`、`file_indexing` 等多项记录时，模态框逐项展示可读名称、百分比、归一状态和原始 message；未知名称仍展示原名。
3. 首次请求加载中、返回空数组、后端 4xx/5xx、网络异常和某一项失败分别展示可区分状态；失败项保留后端错误 message，空数据不显示为请求失败。
4. 打开模态框立即请求；空数组在 30 秒等待窗口内继续轮询，若期间出现活动记录则继续跟踪；存在 pending/processing 项时按 1 秒轮询，成功/失败全部终态后停止；请求失败按退避重试；关闭、卸载和切换文件后不再发请求或写入旧数据。
5. 旧文档解析页面仍使用 `getFileProgress` 查询 `document_parser`，其成功/失败状态和现有上传轮询不改变；文件列表既有上传、重传、重命名、移动、删除和文件夹浏览回归通过。
6. API、转换和交互自动化验证覆盖多进度、空数据、失败状态、非法百分比和异常响应；后端接口的鉴权与 purpose 限制不因新增批量查询而放宽。
