## 目标

- 用最小模型将非文件业务资源纳入现有空间和目录树：仅新增 `node_type` 和 `resource_id` 两个字段，继续复用 `file`、目录关系、查询、重命名、移动和删除能力。
- 所有节点稳定返回 `node_type`，取值为 `file`、`directory`、`resource`；资源节点通过命名空间化的 `resource_id` 同时表达业务资源类型和业务侧 ID，例如 `dataset:12345`、`workflow:67890`。
- 资源节点不具备文件内容。现有文件上传、下载、预览、重新上传、解析及 OpenAI File API 行为保持兼容，资源不会进入对象存储和内容处理流程。
- 管理端在同一列表中识别资源节点，并仅提供重命名、移动、移除和复制资源标识等适用操作。

## 非目标

- 不新增独立资源表、通用目录节点表或第二套目录关系。
- 不新增 `resource_type`、来源、URL、有效状态等字段；资源类型由 `resource_id` 第一个 `:` 之前的命名空间表达。
- 不复制、下载、预览、解析或持久化业务资源内容，不同步外部业务资源的权限和生命周期。
- 不提供通用外部跳转。调用方取得 `resource_id` 后，由对应业务系统决定如何定位和访问资源。
- 不支持资源节点拥有子节点，也不对同一业务资源建立全局唯一约束。

## 当前上下文

- 当前后端已将目录保存为没有真实文件内容的 `file` 行，并通过 `file_closure` 参与目录管理；资源节点可以采用相同方式成为目录树中的叶子节点，无需引入新的树模型。
- `OpenAIFile` 和管理端 `KnowledgeFile` 当前主要依赖 `is_dir`、MIME 和扩展名区分文件与目录。资源使用 `is_dir=false` 时必须增加 `node_type`，否则会被误认为可预览、可重新上传的普通文件。
- #63 正在审批 `file_entry` 目录位置模型。如果其先合入，#71 继续将资源作为普通叶子 entry 写入，不扩展 `file_entry` 表字段；节点是否为资源仍以关联 `file.node_type` 为准。
- 现有内容、URL、预览、裁图、DOM tree、PDF、进度和重新上传接口会访问对象存储或解析链路，必须在这些调用之前统一判断节点能力。

## 方案

### 1. 只增加两个持久化字段

- 在逻辑 `file` 及全部物理分表增加：
  - `node_type varchar(16) NOT NULL DEFAULT 'file'`：允许 `file`、`directory`、`resource`。
  - `resource_id varchar(256) NOT NULL DEFAULT ''`：资源节点必填，文件和目录保持空串。
- 增量迁移先增加带默认值的字段，再将现有 `is_dir=1` 的行回填为 `node_type=directory`；其余历史行保持 `file`。不修改现有 `file_id`、对象存储字段、目录关系和分片规则。
- 资源节点继续使用普通用户文件 ID 和用户空间分片，不增加新的 `FileType` 或 ID 后缀；`node_type` 是资源身份的唯一判断依据。
- 资源节点保存为 `is_dir=0`、`bytes=0`，`bucket`、`path`、`mime_type`、媒体 `type` 和 `extension` 为空。若 #63 已合入，资源使用现有叶子 entry 类型，不要求 `file_entry` 区分普通文件和资源。
- `resource_id` 必须满足 `<namespace>:<business-id>`：命名空间和业务 ID 均不能为空，整体按不透明字符串保存；后端只校验格式和长度，不验证外部资源是否存在。例如 `dataset:12345` 中 `dataset` 即资源类型。
- 对 `(space_code, node_type, resource_id, status)` 增加普通查询索引，不增加唯一索引。同一业务资源可以在不同目录登记多个独立引用，移除其中一个不会影响其他引用或外部原始资源。

### 2. 增加最小创建和查询协议

- 新增 `POST /v1/files/resources` JSON 接口，请求只包含 `name`、`resource_id` 和可选 `ancestor_id`。名称、空间、父目录、同目录重名和锁逻辑复用现有 mkdir/上传规则。
- 创建时在同一数据库事务中写入资源 `file` 行及现有目录关系；若 #63 已合入，则同时使用其既有 entry 双写流程。资源创建不写对象存储、不创建进度、不触发解析任务。
- `OpenAIFile` 增加 `nodeType` 和 `resourceId`，按现有 JSON 命名规则输出 `node_type`、`resource_id`。既有字段全部保留：
  - 普通文件返回 `node_type=file`、`resource_id=""`。
  - 目录返回 `node_type=directory`、`resource_id=""`。
  - 资源返回 `node_type=resource`、命名空间化 `resource_id`、`is_dir=false`、`bytes=0`。
- `/v1/files/find`、`/v1/files/page`、目录列表、详情、路径和祖先查询返回三类节点；分页 `type` 在保留 `dir`、`file` 的基础上增加 `resource`，其中 `file` 仅匹配 `node_type=file`。
- OpenAI 兼容 GET `/v1/files` 增加 `node_type != resource` 条件，只排除资源，保留当前普通文件、目录、purpose、排序和 after 游标行为。
- 现有 rename、move 和 DELETE 直接支持资源：重命名只更新展示名称，不计算扩展名；移动只改变目录位置；删除只移除本地资源引用及目录关系，不调用外部业务系统。
- 第一阶段不提供修改 `resource_id` 的接口。业务资源指向错误时删除旧引用并重新创建，避免一次更新静默改变节点所代表的业务对象。
- 业务资源在外部失效时，本系统不自动改变状态或删除引用；调用方可以保留该引用用于定位，也可以通过 DELETE 主动移除。

### 3. 在内容入口统一阻止资源节点

- 在服务层集中提供节点能力判断，至少区分目录、内容文件和资源；控制器不再仅用 `!is_dir` 判断是否可执行文件操作。
- 上传覆盖、PUT 重新上传、下载、content、预签名 URL、preview、裁图、DOM tree、PDF、进度和解析入口必须在调用对象存储或处理服务前要求 `node_type=file`。
- 对资源调用上述接口时返回稳定的 400 业务错误，明确说明资源节点没有文件内容；不得将空 `bucket/path` 传入存储服务。
- 资源不发送现有 `file.created`、`file.updated`、`file.deleted` 广播，避免文件消费者启动下载或解析；第一阶段也不新增资源广播事件。目录位置和列表更新仍以数据库写入结果为准。
- 描述、标签、城市、purpose、文件版本和解析产物不纳入第一阶段资源能力，避免继续扩大字段和接口范围。

### 4. 管理端按节点类型展示能力

- 扩展 `KnowledgeFile` 的 `node_type` 和 `resource_id`；目录导航、文件预览和资源展示均以 `node_type` 判断，不再用 `is_dir=false` 推断普通文件。
- 资源使用独立图标，类型列显示 `resource_id` 的命名空间，名称旁展示或提供复制完整 `resource_id` 的操作；大小列留空。
- 资源可重命名、移动和移除，不显示预览、下载、上传、重新上传等内容操作。删除确认文案明确为“移除资源引用”，不会删除业务系统中的原始资源。
- 双击目录进入目录，双击普通文件维持现有预览，双击资源不发起 preview 请求。第一阶段不增加资源跳转和管理端登记表单，资源由业务调用方通过创建接口登记。
- 移动目标选择器继续只接受 `node_type=directory`，资源不能进入目录栈或成为祖先节点。

## 风险与边界

- `resource_id` 同时承载类型和业务 ID，依赖调用方遵守命名空间格式。若后续需要独立过滤来源、类型注册、URL 跳转或有效状态，再通过新 issue 增加明确字段，不在本次预留空模型。
- 旧客户端只认识 `is_dir`，在统一目录查询中可能把资源显示为普通文件；后端内容守卫保证不会误操作对象存储。OpenAI 兼容列表排除资源，避免影响既有文件调用方。
- 不设置业务身份唯一约束意味着同一资源可以有多个引用，这是目录组织能力的预期语义；服务端只保证同目录展示名称唯一。
- #71 实现时应基于当时最新 `develop`：若 #63 已合入则复用其 entry 写链路，若尚未合入则复用当前 `file_closure` 写链路，但不得为资源新增独立目录结构。

## 回滚

- DDL 仅新增带默认值的字段，旧文件和目录行为不变；紧急回滚不删除字段或回填数据。
- 如果资源创建上线后需要回滚到完全不识别 `node_type=resource` 的版本，应先停止创建并移除活动资源引用，避免旧版本将资源当作普通文件展示。
- 内容能力守卫应与资源读取能力一起保留；不能仅回滚守卫而继续保留资源数据。

## 验证

1. **迁移与模型**：在 MySQL 5.7+ 执行全量初始化和增量迁移，确认所有文件分表字段一致；运行 jOOQ generate 和编译，验证历史目录回填为 `directory`、其他历史节点为 `file`，原有 ID、存储字段和目录关系不变。
2. **创建接口**：覆盖根目录和子目录创建、`resource_id` 命名空间格式、字段长度、父节点不存在或非目录、跨空间父节点、同目录同名以及事务失败回滚；断言创建过程不调用对象存储、进度或解析服务。
3. **统一查询**：构造文件、目录和资源混排，验证 find/page/详情/路径/祖先查询返回稳定 `node_type` 和 `resource_id`，分页 `type=dir|file|resource` 结果及总数正确。
4. **兼容查询**：验证 OpenAI GET `/v1/files` 继续返回当前文件和目录结果但不返回资源，purpose、排序、after 和普通文件 JSON 保持兼容。
5. **目录操作**：覆盖资源重命名、移动和删除，确认重命名不产生扩展名，移动后目录和祖先关系正确，删除仅清理本地节点及目录关系，不影响具有相同 `resource_id` 的其他引用。
6. **内容隔离**：对 URL、content、preview、重新上传、裁图、DOM tree、PDF、progress 和解析接口传入资源 ID，断言全部在存储或处理 mock 调用前返回明确 400；普通文件成功路径保持不变。
7. **管理端验收**：执行 `cd web && npm run type-check && npm run lint:check && npm run build`，人工确认三类节点混排、资源图标与标识复制、操作菜单、删除文案、移动目标限制，以及资源双击不会请求 preview。
8. **后端回归**：执行资源相关定向测试及 `cd api && mvn test`，重点回归 mkdir、move、page、closure/entry 事务和现有文件上传、列表、详情、内容与删除测试。
