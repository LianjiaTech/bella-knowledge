## 目标

为单个和批量 `file_id` 查询文件树展示路径提供一套可扩展的读取方案。方案只向调用方返回路径字符串，不改变当前文件树语义；在允许最终一致的前提下，把正常读请求从“按目录深度读取父链”收敛为受控的索引/快照读取，同时保留迁移期和异常数据的可诊断降级路径。

本方案以当前仓库事实为边界：`file_entry` 按空间分片并以 `parent_entry_id` 维护树，`FileEntryRepo.pathFiles` 沿父链组装路径，`FileRepo.getPathFiles` 在 entry 未就绪时回退 `file_closure`；`file.path` 是对象存储路径，不能作为文件树展示路径使用。现有 `entry`、`closure` 双写和 `read-mode`/`write-mode` 切换逻辑继续作为文件树能力的事实来源和回退能力。

## 方案

### 1. 路径契约与接口边界

采用新的统一规范路径：以 `/` 开始，根目录本身表示为 `/`，从空间根到目标节点按 `filename` 依次拼接，空间标识不放入路径字符串。例如根下 `a` 目录中的 `b.txt` 返回 `/a/b.txt`。空间根不是一个虚拟路径段，跨空间移动后路径仍按目标空间根重新计算。

路径段按 UTF-8 的 RFC 3986 path-segment 规则编码：`/`、`%`、控制字符以及会改变分段含义的字节必须 percent-encode，普通 Unicode 文件名保持可读；不做大小写折叠、不做 Unicode 规范化、不把重名合并。重名在同一父节点下仍由现有 `(space_code, parent_entry_id, filename)` 唯一约束禁止，历史异常重名不在本方案修复范围内。实现必须集中使用一个 path encoder，禁止分别在单个和批量接口中拼接字符串。

该编码规则是 `info` 和新增路径接口的统一输出契约。实现阶段将把 `FileService.info` 的现有逐段原样拼接迁移为调用同一 encoder；普通文件名的结果不变，包含 `/`、`%` 或控制字符的历史路径会产生明确的规范化行为变化。发布说明和回归用例必须覆盖这一兼容边界，不能让旧 `info` 与新接口对同一 `file_id` 返回两种表示。

新增两类只读能力，具体 HTTP 路由沿现有文件 API 的版本和鉴权约定落地：

- 单个：`getPath(file_id)`，返回一个路径字符串；不存在、已删除或无权访问按现有文件查询语义返回 not-found，不返回对象存储 `file.path` 或其他文件字段。
- 批量：`getPaths(file_ids)`，输入为 `file_id` 数组，输出为 `file_id -> path string` 映射。成功项的 value 始终是路径字符串；不存在、已删除、暂时无法解析或异常的 ID 不出现在映射中，以此支持部分成功而不扩展每项返回元数据。服务端记录缺失、未就绪和异常的分类指标，调用方通过缺少对应 key 判断该项没有可返回路径。

批量接口单次最多接收 500 个 ID，限制请求体和响应体大小；超过上限直接拒绝，调用方自行分片并按原输入顺序合并结果。服务端数据库查询按 500 个 ID 以内再次按物理分片、空间和 SQL `IN` 块聚合，不提供 offset 分页；需要更大规模导出时另立异步任务需求。本上限低于当前 SQL `IN` 分块阈值，给路径长度和响应体留出余量，后续以压测结果调整为配置而非改变契约。

### 2. 统一存储模型：物化路径快照，缓存不是唯一事实来源

单个与批量共用一张按 `space_code` 分片的路径快照表，建议命名为 `file_path_snapshot`，每个活动 `file_entry` 对应一行，至少包含：`space_code`、`file_id`、`path_value`、`materialized_version`、`state`（`READY`/`STALE`/`MISSING`）、`mtime`。以 `(space_code, file_id)` 唯一约束并增加按 `file_id` 的查询索引；表结构和全部分片初始化脚本保持与 `file_entry` 同步。路径快照只复制展示路径，不复制文件实体字段和对象存储路径。

选择“物化快照 + 异步更新 + 实时回退”，不选择纯父链计算、单纯进程缓存或在 `file_entry` 中直接增加大字段：

- 纯父链计算读放大随深度增加，批量虽然可按层聚合，但每次都跨层访问；适合作为回退，不适合作为高频路径服务的主路径。
- 进程/分布式缓存无法独立解决批量分片、冷启动、失效传播和迁移恢复，且会增加缓存淘汰和双写一致性复杂度；快照表先提供可恢复的共享缓存，后续若监控证明热点明显，再在其上增加短 TTL 的只读缓存。
- 把完整路径放进 `file_entry` 能减少一次 join，但路径重命名/移动会产生大范围行更新、放大现有树写事务，也会让窄表膨胀；独立窄表把路径读写与文件树主记录解耦。
- 新增只更新单节点快照；文件重命名只更新单节点，但目录重命名与目录移动一样以该目录为子树根，异步失效并批量重建所有后代快照；正常路径读取为一次按键查询，批量读取为按分片聚合的批量查询。代价是快照存储约为每个活动节点一行加路径字符串，并存在事件处理窗口内的旧路径。

快照表不是文件树事实来源。读取优先使用 `READY` 或允许提供旧值的 `STALE` 快照；没有快照、快照为 `MISSING`、事件重建失败、数据迁移未完成或检测到异常时，调用现有 `file_entry` 父链解析，必要时复用 `FileRepo.getPathFiles` 的闭包回退。回退成功后异步 upsert 快照，不在用户请求事务内递归更新整个子树。

### 3. 变更传播、版本和异步任务

在现有文件创建、重命名、同空间移动、删除和跨空间移动的主事务中增加同事务 outbox 事件，不改变现有 `file`、`file_entry`、`file_closure` 的提交顺序和回滚语义。事件至少包含空间、操作类型、根 `file_id`/`entry_id`、源/目标空间（跨空间时）、变更版本和幂等事件 ID。消费者按空间和根节点合并事件，避免连续重命名/移动为每次都重建完整子树。

各变更的处理规则如下：

- 新增：事务提交后为单节点生成快照；若父链尚未可读，保留 `MISSING`/待重建状态并重试。
- 重命名：文件节点只产生单节点失效事件；目录节点产生子树失效/重建事件，消费者通过 `file_entry` 分层遍历目录及全部后代并批量重算。由于文件名唯一性仍由 `file_entry` 约束保证，不额外引入路径唯一性。
- 同空间移动：事件以被移动节点为根，消费者通过 `file_entry` 分层遍历其后代并批量重算；不把每个后代的更新加入移动主事务。任务按批次提交、可重试、幂等 upsert。
- 删除：先让快照进入 `MISSING`，再异步删除/清理快照；读取按活动文件语义返回 not-found，不返回删除前路径。异常中断时由定期清理任务回收孤立快照。
- 跨空间移动：源空间快照标记删除，目标空间按迁移后的 `file_entry` 子树重新生成；任务携带迁移版本，旧空间事件不得覆盖目标空间快照。沿用当前代码对非空目录跨空间移动的 `write-mode=entry` 约束和闭包停写要求，不为路径能力放宽该边界。

事件消费者使用版本比较和幂等键。`materialized_version` 不使用现有 `file.version`，而使用每个空间内单调递增的 outbox sequence；该 sequence 在产生变更的同一空间事务中分配并写入事件，所有影响该空间快照行的新增、重命名、移动、删除事件共享可比较的序列。跨空间移动在源空间和目标空间分别分配各自空间序列，源/目标快照只与所属空间序列比较。只有不低于当前快照版本的事件可以写入，较旧事件丢弃并计数。目标是正常情况下 99% 变更在 60 秒内收敛、无持续超过 5 分钟的 `STALE`；这些是运维 SLO，不把最终一致窗口伪装成强一致保证。快照读命中不阻塞写事务；若业务未来需要强一致，应另加显式 fresh-read 语义，不改变本接口默认行为。

### 4. 与现有分片、父链和闭包回退兼容

路径查询先通过现有文件 ID 查询获得 `space_code`，再把 ID 按空间分片路由到 `file_path_snapshot`；批量查询先按现有 file 表/ID 路由完成 `file_id -> space_code` 映射，再按空间分组读取快照，避免假设 file 表和 `file_entry` 共享同一分片键。没有空间映射的 ID直接作为部分失败处理，不跨所有空间扫描。

`file_entry` 仍是展示名称和父子关系的主记录；快照重建只调用现有 `queryActiveByFileId`、父链/分层遍历和统一编码器，不复制或改写闭包表。`FileEntryRepo.ancestorFileIds` 已有按层聚合的批量父链读取，可作为重建任务的实现基础，但任务必须沿用 `MAX_TREE_DEPTH`、SQL `IN` 分块和环检测，不能为了快照绕过现有异常保护。

读取模式兼容矩阵如下：

- `read-mode=entry` 且 `file_entry` 已就绪、快照命中：直接返回快照路径。
- `read-mode=entry` 下快照未命中/过期或 entry 尚未回填：先尝试现有 entry 父链；entry 抛 `EntryReadNotReadyException` 时遵循 `FileRepo.getPathFiles` 的 `closureWriteEnabled` 判断，闭包仍在写则回退闭包，闭包已停写则暴露未就绪错误并记录告警。
- `read-mode=closure`：禁用 entry-derived 快照的读取和重建，始终沿既有闭包链路读取；切回 `read-mode=entry` 前不把 closure 结果写入 entry 快照。这样运维切换 closure 时不会绕过既有回退开关。
- `write-mode=closure`：除上述 closure 读模式外，不允许路径快照任务把 entry 当作已写入事实；待切回 `dual`/`entry` 并完成回填校验后再恢复快照重建。
- `entry` 与闭包不一致：不自动选择较“新”的一侧覆盖另一侧；按当前回退策略返回可读结果，同时记录 file ID、空间和版本，交由对账/回填任务处理。路径方案不改变已有文件树双写迁移和止血开关。

### 5. 后台任务、监控和实现边界

实现阶段新增三类后台能力：事件 outbox 投递与重试、按事件重算单节点/子树、周期性对账与孤儿清理。任务必须具备最大重试次数、死信/人工重放入口、按空间限流和批量大小配置；目录大子树继续遵循现有跨空间移动告警阈值，不在用户请求中同步展开。

新增指标至少包括：单个/批量请求 QPS、命中率、批量 ID 数、快照读延迟和回退延迟（p50/p95/p99）、按原因分类的 miss/stale/not-found/异常数、outbox backlog/处理延迟/重试/死信、重建节点数和失败数、路径写入对文件创建/移动/重命名 p95 的影响、对账不一致数及最大收敛时间。日志不得输出完整敏感路径，使用 file ID、空间和哈希/长度做关联。

非目标：本 issue 不实现接口、表结构、缓存、任务或迁移脚本；不修改现有文件树语义、闭包读写和跨空间移动约束；不返回文件元数据；不承诺强一致或任意规模同步批量请求；不把对象存储 key 重新解释为展示路径；不处理历史重名、环、孤儿 entry 等数据修复本身。`info` 的保留接口会迁移到统一路径编码，但不在本 issue 中提供旧/新两套并行表示。

## 验证

### 功能与一致性验收

1. 使用根节点、嵌套目录、Unicode、空格、`%`、包含 `/` 的特殊文件名和删除/重建场景，逐项确认单个返回符合 `/` 根路径和 path-segment 编码规则；同一 `file_id` 的单个与批量结果必须完全相同。
2. 验证批量输入 0、1、500、501 个 ID，以及跨多个 file 分片和多个空间的混合输入；确认成功项只返回路径字符串，未知、删除、未就绪和异常项被省略且不影响其他成功项；超过上限被拒绝而不触发全表扫描。
3. 对新增、文件/目录重命名、同空间移动、非空目录移动、删除、跨空间移动分别记录空间级 outbox sequence，验证目录重命名和移动会覆盖全部后代、事件幂等、乱序事件不会覆盖新快照，子树最终路径与逐节点实时父链计算一致。
4. 在 `read-mode=entry`、`read-mode=closure`、`write-mode=dual`、`write-mode=entry` 和迁移未完成窗口分别制造快照 miss、entry 缺失、闭包缺失和双边不一致，确认 closure 模式不会读取 entry 快照，其他模式的回退/失败行为与现有 `getPathFiles` 规则一致，不破坏列表、计数和移动能力。
5. 运行周期性对账：随机抽样和全量分批比较快照路径与当前 `file_entry` 父链编码结果，校验 0 个静默错误；对异常深度、环、缺父、file_entry 指向缺失 file 的数据确认进入告警/死信而不是生成错误路径。

### 性能与容量验收

建立固定深度（1/8/32/64）、固定路径长度、热点/冷门 ID、单空间/跨空间和目录子树移动的压测数据集，至少覆盖：

- 单个快照命中、单个 miss 回退、连续 miss 后回填；
- 批量 10/100/500 个 ID，命中率 100%、混合 miss 和跨分片；
- 并发创建、重命名、移动与读取，包含大子树和跨空间移动；
- outbox 延迟、消费者重启、重复投递、死信重放和全量重建。

验收目标为：单个命中 p95 不高于 10 ms，500 ID 批量命中 p95 不高于 100 ms（在与现有基准相同的数据库和压测规模下）；回退路径的 p95 不劣于现有 `getPathFiles` 基线 10%，且不因批量请求退化为逐 ID 查询；文件写入/移动/重命名 p95 增幅不超过 5%；正常负载下 outbox backlog 可持续清空，99% 路径变更 60 秒内收敛、5 分钟后仍为 `STALE` 的比例为 0。若真实容量基线无法达到目标，必须在 Plan 批准后的实现 PR 中给出实测值、瓶颈和调整后的明确上限，而不是静默放宽验收。

### 发布与回滚

先建表和回填工具但关闭快照主读，完成快照与父链对账后按配置启用“命中优先、回退可用”；观察命中率、延迟、事件积压和一致性指标，再逐步提高异步重建范围。异常时关闭快照主读和消费者，保留现有 entry/closure 读写；快照表可独立清空并重新回填，不回滚或删除 `file_entry`、`file_closure` 数据。只有在确认 `write-mode=entry`、闭包回退不再需要且完成最终对账后，才评估清理旧兼容路径，超出本 issue 范围。
